# Share an editing session

::warning{title="Experimental API"}
The collaboration API is experimental in version 1.0. A minor release can
change it. Pin the exact Editor version on the client and the server, and read
the changelog before you update.
::

Ginko Editor can share a document through a host transport. It uses ProseMirror
operations to merge text changes. The host owns authentication, authorization,
storage, recovery files, and publication. The editor does not open a Convex
connection or create accounts.

The package provides two boundaries:

- `@lupinum/ginko-editor/collaboration`: a Vue-compatible editing session,
  its state and error types, recovery helpers, and presence types.
- `@lupinum/ginko-editor/runtime`: the shared schema, the protocol and
  transport types, strict operation decoding, and server checkpoint
  validation. This entry does not import Vue views or browser globals.

Import transport types such as `CollaborationTransport` and
`CollaborationHead` from `@lupinum/ginko-editor/runtime`. Use `import type` in
browser code so the bundle does not include server validation.

Use the same Editor package and Content policy on the client and server. A
schema revision identifies the document schema and the operation format. A
protocol version identifies the message envelope. A policy revision
identifies the host's permitted components and properties. An epoch
identifies one generation of a document. Replacing a document starts a new
epoch.

## Mount one session

The host first opens an authorized document and obtains its current snapshot.
It supplies three transport operations: subscribe to the current head, pull
accepted operations, and push a batch at an exact version.

```ts
import { createEditorCollaboration } from '@lupinum/ginko-editor/collaboration'

const session = createEditorCollaboration({
  snapshot: opened.snapshot,
  clientId: opened.clientPrefix + crypto.randomUUID(),
  transport,
  recovery: savedRecovery,
  onRecovery(value) {
    if (value) sessionStorage.setItem(recoveryKey, JSON.stringify(value))
    else sessionStorage.removeItem(recoveryKey)
  },
})
```

```vue
<GinkoEditor
  v-model="sourcePreview"
  :collaboration="session"
  :authoring-kit="authoringKit"
/>
```

Keep the session in a `shallowRef` or an ordinary variable. Do not make its
internal editor state deeply reactive. One session belongs to one mounted
editor. Create a new session and remount when switching documents, epochs, or
content policies. Await `flush()` before leaving; keep the editor mounted if
flush fails.

In shared mode, the session snapshot supplies the initial document. `v-model`
receives a source preview. Changes to that prop do not replace the shared
document. Source view is read-only. A successful `flush()` means all pending
operations have been accepted and the local source preview is current. It does
not publish content. Another writer can still edit after the flush.

The default status shows connecting, saving, saved, offline, and recovery
states. The `collaboration` slot receives `state` and `session` if the host
needs its own status control. Use `session.subscribe()` for application state
and call the returned cleanup function when the host unmounts.

## Handle connection and server failures

`session.state.code` gives the reason for an `offline`, `error`, or `stale`
status:

| Code | Status | Meaning and host action |
|---|---|---|
| `offline`, `timeout`, `unavailable` | `offline` | The session keeps local edits and retries automatically. |
| `rejected` | `error` | The server refused the unsent changes. Offer `discardPendingAndResync()`. |
| `forbidden` | `error` | Access was revoked. Keep the recovery copy and close the editor. |
| `conflict`, `internal` | `error` | The server history is inconsistent. Offer `retry()` and the recovery download. |
| `storage` | `error` | `onRecovery` threw. Free storage, then call `retry()`. |
| `schema_mismatch`, `policy_mismatch`, `replaced`, `history_expired` | `stale` | Keep the recovery copy and reopen the document. |
| `limit` | any | A local change was refused because it is too large. |

A transport signals a failure through the error it throws:

- Throw `CollaborationConnectionError` when the network is not available.
- Throw `new CollaborationError('forbidden', message)` for revoked access.
- Throw `new CollaborationError('unavailable', message)` for a temporary
  server failure.
- A server `CollaborationError` code, a `data.code` value such as Convex
  `ConvexError` data, or an HTTP `status` also classifies the failure. Status
  408, 425, 429, and 5xx retry. Status 401 and 403 stop.

Retries use full jitter: each wait is a random time up to a bound that
doubles from 1 second to 30 seconds. A new server head or the browser
`online` event ends the wait early. Each pull and push has a 15-second
limit. Set `requestTimeoutMs` and `backoff` to change these values.

`retry()` sends the same pending changes again. After a `rejected` state,
call `discardPendingAndResync()`. It gives the unsent changes to `onDiscard`,
removes them, and continues from the last accepted document. If `onDiscard`
throws, the session keeps the changes. `flush()` rejects with a
`CollaborationError` that has a `code`.

```ts
const session = createEditorCollaboration({
  // ...
  onDiscard(recovery) {
    offerDownload(JSON.stringify(recovery))
  },
})

if (session.state.code === 'rejected') session.discardPendingAndResync()
```

## Validate each write

The backend checks document access on every read and write. Do not trust a
room ID, client ID, source preview, or snapshot supplied by a browser.

```ts
import { applyCollaborationSteps } from '@lupinum/ginko-editor/runtime'

const accepted = await applyCollaborationSteps(storedSnapshot, batch, {
  policy: hostPolicy,
  output: hostOutputOptions,
})

// In one database transaction:
// 1. Store accepted.snapshot.
// 2. Append the accepted operations and authenticated client identity.
// 3. Store accepted.markdown with the same epoch and version.
```

`applyCollaborationSteps()` rejects an incorrect version or document fence,
an unknown protocol version, unknown operations, malformed positions, unknown
schema attributes or marks, invalid attribute values, unsafe link URLs,
unsupported metadata, and results outside the Content policy. It checks the
result against the schema and derives Markdown from the accepted document. It
never accepts a browser's Markdown checkpoint.

Attribute values have fixed rules. For example, a heading level is a whole
number from 1 to 6, code language and filename are one line of text, and a
link target uses the same URL rules as Content: `https`, `mailto`, `tel`,
local paths, and `#` anchors.

Clients send `protocolVersion: 1` with pull and push requests. If your
backend validates request arguments strictly, accept this optional field.

Seed or replace a room with `createCollaborationSnapshot()`. It refuses source
that requires source-only editing. A replacement must check the current fence
and version in the same authorized transaction, then start a new epoch. Keep
old published content until the host explicitly publishes the replacement.

For Convex, query the current head reactively with `ConvexClient.onUpdate()` and
use generated, typed query and mutation references for pull and push. Check
the membership or document permission inside each function. Scope client IDs
to the authenticated member and add a random identifier for each session.
Return accepted operations after a version conflict so the editor can rebase
and retry. Do not use last-write-wins Markdown updates.

The repository's `test/fixtures/convex-collaboration` directory contains an
executable local example with signed test identities. It demonstrates
authorization, bounded history reads, version conflicts, revocation,
replacement, publication, and pruning. Its test authentication and membership
tables are fixture code. Use the host application's real authentication and
document permissions in an application.

## Store checkpoints and history separately

Store the ProseMirror document as an encoded JSON string. Its nested tree must
not become deeply nested database fields. Store the derived source in a
separate record when the two representations could exceed the database's
document-size limit. Both records carry the same epoch and version.

The server snapshot is the authority for the active editing session. Markdown
is a derived, versioned checkpoint for Content readers, export, and
publication. It can be rebuilt from the snapshot. Do not independently edit
both representations.

Publish an exact `{ epoch, version }` checkpoint after checking that it is still
current. Record the publication epoch as well as its version: version numbers
restart after replacement. A failed comparison requires the host to refresh
and show the newer draft.

History queries must use an index and a bounded page. The provided protocol
limits a document to 512 KiB, a batch to 256 KiB, and a batch to 128 operations.
A client keeps each original transaction in one outgoing batch. Read pages
must preserve operation order and return their actual start and end versions.

Set an explicit retention policy in the host. Keep a minimum retained version.
If a disconnected client needs older operations, return `status: 'stale'` with
reason `history`. Do not silently discard its pending edits or substitute a new
snapshot. Delete old log pages in bounded jobs. Replacing a document also
requires eventual cleanup of the old epoch's log.

## Recover pending changes

Supply `onRecovery` when unsent edits must survive reload. Persist the value
synchronously in host-owned browser storage; throwing stops editing and keeps
the current document available. The editor does not promise durable recovery
when this callback is omitted.

The session calls `onRecovery` at most once every 300 milliseconds while the
user types. It also calls it immediately when the page is hidden or unloaded,
and from `flushRecovery()`, `flush()`, `discardPendingAndResync()`, and
`close()`. Set `recoveryDelayMs: 0` to write after every change. Remote
changes do not write a recovery copy when there is no local work.

A recovery copy includes the confirmed base, pending operations, transaction
groups, and the resulting document. Reopening checks its format and document
fence, then rebases pending operations over accepted server history. A lost
acknowledgement does not duplicate an accepted operation.

Use `readCollaborationRecovery(storedJson)` to read untrusted storage. It
returns one of three results:

- `current`: pass `result.recovery` to a new session. Session construction
  then checks the document, operations, limits, and fences.
- `converted`: the copy uses another schema revision. Its operations cannot
  be rebased, so `result.markdown` contains the pending document as Markdown.
  Show it to the user for a manual merge.
- `unreadable`: offer the stored text as a download.

`parseCollaborationRecovery()` only checks the storage shape. Keep an invalid
copy available for download; do not silently discard it or enable a fresh
writable session over it.

Only one live session may own a client ID. Browsers can copy `sessionStorage`
when a tab is duplicated or opened from another tab. Claim an exclusive Web Lock
for the client ID before opening either a new or recovered session, and release
it after closing that session. If another tab owns the ID, offer the recovery
download and a deliberate reopen with a new identity. Do not replay the same
pending operations under a second identity.

The client bounds recovery to 2,048 pending operations, 2 MiB of encoded
operations, and a 4 MiB recovery budget for local changes. Rebased remote
changes can enlarge a recovery file; reopening accepts up to 16 MiB. A local change that would
exceed a limit is refused before replacing the local document. Reconnect to
continue writing. The limits describe recovery capacity, not an offline-first
database.

Revoked access, a changed schema or policy, a new epoch, or expired history
must remain visible. The default control can download the pending recovery
JSON. Keep that copy before reopening or importing its content into a new
document. Never apply old operations to a different epoch automatically.

## Change the schema revision

`editorSchemaRevision` changes when an Editor release changes the document
schema or an operation format. A test in this repository compares a
fingerprint of the schema and operation types with a recorded revision, so a
schema change cannot ship without a new revision.

Clients and rooms with different revisions cannot exchange operations. Use
this procedure when you deploy a release with a new revision:

1. Deploy the new Editor package to the server and the browser together.
2. For each room with the old revision, read its accepted Markdown checkpoint
   in one authorized transaction.
3. Call `createCollaborationSnapshot(markdown, { epoch: newEpoch, policy,
   policyRevision })`. Store the new snapshot with version 0, a new epoch, and
   the new revision. Reset the minimum retained version.
4. Keep the published content until the host publishes again.
5. Delete the old epoch's operation log in bounded jobs.

You can also run steps 2 and 3 when a user opens a room with the old
revision. Old browser sessions become `stale`. Their recovery copies return
`converted` from `readCollaborationRecovery()`; show the Markdown so the user
can merge it by hand.

## Understand concurrent controls

Body text merges through ProseMirror. Component controls change individual
properties. Independent properties preserve each other; two changes to the
same property use the last accepted operation. Titles in separate property
inputs are field updates, not character-level shared text. Code language and
filename controls also update separate fields. Image replacement preserves
unrelated properties, including another writer's description.

Shared tables support cell editing and inserting, deleting, or
duplicating body rows. Column layout, alignment changes, and row moves are disabled during a shared
session. ProseMirror does not preserve pending edits through arbitrary node
moves, and concurrent row and column layout changes can produce incompatible
rectangles. Local tables retain their full controls. Merged cells and custom
cell widths are rejected because the Content checkpoint cannot preserve them.

## Show other collaborators

Presence is optional. Add a `presence` channel to the transport to show other
collaborators' carets and selections. Presence records are separate from
document operations. Do not treat a caret as proof that a writer's changes
have been accepted.

```ts
import type { CollaborationTransport } from '@lupinum/ginko-editor/runtime'

const transport: CollaborationTransport = {
  subscribe, pull, push,
  presence: {
    publish: update => client.mutation(api.rooms.publishPresence, { roomId, update }).then(() => {}),
    subscribe: onPeers => client.onUpdate(api.rooms.presence, { roomId }, onPeers),
    leave: clientId => client.mutation(api.rooms.leavePresence, { roomId, clientId }).then(() => {}),
  },
}

const session = createEditorCollaboration({
  // ...
  transport,
  user: { name: account.displayName, color: account.color },
})
```

The session publishes its selection when it changes, at most every 100
milliseconds, and again every 10 seconds. Positions refer to the last
accepted document version, which the record includes. The session maps other
collaborators' positions through accepted operations and through its own
unsent operations before it shows them. It hides a selection that it cannot
map yet. It removes a collaborator after 30 seconds without a new record.
Without `user`, the session shows others but does not publish. Set
`presence: false` to turn presence off.

`session.extension` shows the carets. Each caret has a name label that is
hidden from assistive technology. Show a collaborator list for screen reader
users from `session.peers` and `session.onPeersChange()`:

```ts
const peers = shallowRef(session.peers)
const stopPeers = session.onPeersChange(value => { peers.value = value })
```

Style the carets with the `.ginko-collab-caret`,
`.ginko-collab-caret__label`, and `.ginko-collab-selection` classes. Each
caret and selection sets `--ginko-collab-color`.

On the server, check document access for every presence read and write. Use
`readCollaborationPresence()` from the runtime entry to validate the record.
Check that the client ID belongs to the member. Take the display name from
the account, not from the browser. Set `updatedAt` to the server time and
delete records that have not changed for 30 seconds. The
`test/fixtures/convex-collaboration` example stores presence in its own
table, reads only records that have not expired, and deletes expired records
with a scheduled function.
