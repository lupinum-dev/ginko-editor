# Upload and choose images

The editor owns insertion, replacement, pending state, and cancellation. Your
application owns storage, access checks, image queries, and saving the document.

## Return an image reference

`image-upload` receives `(file, { signal })`. `image-picker` receives
`{ signal, current? }`. Both can be provided together. **Add image**, `/image`,
and **Replace image** use the same inline flow with Upload and Browse images
controls. With only a picker, the placeholder shows Browse images and does not
claim file drops.

```ts
import type { EditorImage } from '@lupinum/ginko-editor'

const storedImage: EditorImage = { id: 'asset-123', alt: 'A forest path' }
const hostedImage: EditorImage = { url: '/images/forest.jpg', alt: 'A forest path' }
```

`EditorImage` requires a non-empty `id` or `url`. An id can include a display URL.
Supported optional fields are `alt`, `title`, `width`, `height`, `fit`, `quality`,
`focalX`, `focalY`, `cropX`, `cropY`, `cropWidth`, and `cropHeight`. Numeric
metadata must be finite. The active Content policy still validates the result.
Display labels and filenames belong in the host's library records, not this type.
The existing upload callback continues to return `Partial<AssetInfo>` for
compatibility; the editor validates its result at runtime.

Provide an `asset-provider` to resolve stored ids. The provider owns display URL
construction and reverse parsing; its safe resolved URL takes precedence over
the stored source. Persist a durable reference, not a temporary preview URL.
Use `image-output="markdown"` for native Markdown. The default `mdc` output
preserves supported presentation metadata.

`current` contains the image being replaced when available. Use it to identify
the current asset in your picker. It does not contain your whole storage record.
Resolve the callback with `null` when the author cancels. Reject with a readable
error to leave a retryable placeholder or keep the original replacement target.

## Connect the shared picker

`GinkoImagePicker` is a controlled Vue dialog. It renders the `images` array you
provide. It never queries storage or filters records by itself. This example
uses two site images and filters them in the host. Replace those records with
your application's image library.

```vue
<script setup lang="ts">
import { computed, onBeforeUnmount, ref } from 'vue'
import {
  GinkoEditor, GinkoImagePicker,
  type EditorImage, type EditorImagePickerItem, type ImagePicker,
} from '@lupinum/ginko-editor'
import '@lupinum/ginko-editor/style.css'

const source = ref('')
const open = ref(false)
const query = ref('')
const library: readonly EditorImagePickerItem[] = [
  { key: 'forest', label: 'Forest path', image: { url: '/images/forest.jpg', alt: 'A forest path' } },
  { key: 'river', label: 'River', image: { url: '/images/river.jpg', alt: 'A river' } },
]
const images = computed(() => library.filter(item =>
  item.label.toLowerCase().includes(query.value.toLowerCase()),
))
let finish: (image: EditorImage | null) => void = () => {}

const pickImage: ImagePicker = ({ signal }) => {
  finish(null)
  return new Promise(resolve => {
    let settled = false
    const abort = () => complete(null)
    function complete(image: EditorImage | null) {
      if (settled) return
      settled = true
      signal.removeEventListener('abort', abort)
      open.value = false
      finish = () => {}
      resolve(image)
    }
    finish = complete
    if (signal.aborted) return complete(null)
    signal.addEventListener('abort', abort, { once: true })
    query.value = ''
    open.value = true
  })
}
onBeforeUnmount(() => finish(null))
</script>

<template>
  <GinkoEditor v-model="source" :image-picker="pickImage"
    :enable-files="false" :enable-video="false" />
  <GinkoImagePicker :open="open" v-model:query="query" :images="images"
    @select="finish" @update:open="value => { if (!value) finish(null) }" />
</template>
```

Each `EditorImagePickerItem` has a stable `key`, a display `label`, and an
`image: EditorImage`. Optional `thumbnailUrl` supplies a separate preview.
Without it, the dialog uses `image.url`; id-only records need a thumbnail URL
if you want a preview.

| Picker prop | Default and purpose |
| --- | --- |
| `open` | Required controlled visibility |
| `images` | Required readonly item array; already filtered by the host |
| `query` | Empty string; the current search text |
| `loading` | `false`; shows progress and disables Load more |
| `error` | Optional host error shown in the dialog |
| `hasMore` | `false`; shows Load more when true |
| `enableUpload` | `false`; shows an Upload button that emits `upload` |
| `messages` | Optional `EditorMessages` overrides |
| `overlayContainer` | Optional element or selector for the dialog portal |

Events are `update:open(boolean)`, `update:query(string)`, `select(EditorImage)`,
`load-more`, and `upload`. Selecting an image emits `select` before closing.
Resolve your promise once; a subsequent close event must not overwrite the
selected image with cancellation.

For a server library, react to `update:query`, reset pagination, and request the
new results. Pass those results as `images`; use `loading`, `error`, and
`has-more` to represent your request state. `load-more` asks the host for the next
page. The `upload` event asks the host to open its upload UI; it does not start
`image-upload` automatically. Keep authentication and unused-file cleanup in
that host code.

## Preserve pending work

The editor keeps pending image operations outside the document. They never
appear in Markdown. Their insertion point follows intervening text edits;
replacements still target the original image. Completion cannot replace a
different image after the target is removed or changed.

Respect the callback's `signal`. Abandoned operations are cancelled when their
target, document, relevant handler, editability, or editor lifetime changes.
A failed or cancelled replacement keeps the original image. The signal also
lets an upload host clean up a newly stored file that could not be inserted.
A successful insertion does not abort that operation merely to clean up its UI.

Pending image operations count toward `hasPendingChanges()` and `pending-change`.
`flush()` returns `{ ok: false, error }` with code `image_upload_pending` while
an operation remains unfinished. Finish or remove it before closing, replacing
the document, or navigating. Do not call `flush()` inside the upload or picker
callback before returning its image: that same operation is still pending.
After a successful flush, await your application's save operation.

Keep replaced and undone assets while application history can still reference
them. The editor does not delete host files or decide when history expires.

## Existing host events

When neither `image-upload` nor `image-picker` is provided, the editor emits
`request-image`. The event's `EditorAssetRequest` has a one-shot
`complete(asset | null): boolean`. Complete with `null` on cancellation.
`request-file` and `request-video` use the same request pattern.

These event requests require their original document, selection, mode, and
editability to remain valid. They do not follow intervening edits like the new
image callback flow. Returning false means no asset was applied. Do not connect
both image mechanisms to the same host dialog: configured callbacks take
precedence over the legacy image event.

Set `enable-images`, `enable-files`, or `enable-video` to false when the host
has no corresponding insertion flow. Existing media remains readable and
removable. The local playground's IndexedDB images are browser-local examples;
they are not published assets or shared across devices.
