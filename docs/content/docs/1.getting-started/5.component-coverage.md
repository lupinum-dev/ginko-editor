# Component coverage

Ginko Content owns what a document means: component names, property values,
slots, parent/child rules, and media references. Ginko Editor uses that contract
to decide what it can edit without losing meaning. A host kit adds labels,
controls, insertion recipes, and canvas hints. The host's renderer supplies the
real reading preview.

## Built-in layout kit

The editor exports `ginkoLayoutKitSource` from `@lupinum/ginko-editor/authoring`.
Its policy is the Ginko Docs component policy. It contains 32 component tags and
26 recipes. A Ginko Docs site renders the same tags with its `Mdc*` components.
See [Layout blocks](/docs/getting-started/layout-blocks) for each block.

| Docs tags | Visual authoring in the layout kit |
| --- | --- |
| `note`, `warning`, `error`, `success`, `idea`, `info` | Callout recipes, inline title, compatible variant switch, properties, and editable default content |
| `aside`, `excerpt` | Recipes, inline label, properties, and editable default content |
| `layout`, `column` | Two-column recipe; nested content; width and layout controls. A column must remain inside a layout. |
| `tabs`, `tab`, `code-group` | Tab strip: select, add, rename, and remove items. One tab is visible at a time. |
| `accordion`, `accordion-item` | Item titles on the canvas; items collapse in this view only; add and remove items |
| `steps`, `cards`, `card`, `timeline`, `timeline-item`, `code-tree`, `quiz`, `quiz-question` | Numbered steps, card grids, timeline markers, and item lists with an add control |
| `collapse`, `center`, `dropcap`, `figure`, `files`, `kbd`, `read-more`, `toc`, `api` | Recipes, properties, and editable default content. Structured properties use a JSON field. The canvas does not imitate their reading layout. |
| `img` | Native editor image handling; the host supplies storage and URL resolution. This is separate from the kit. |

Rendering support is not visual editing support. The canvas is a stable writing
view. It is not an exact copy of interactive tabs, quizzes, or other reading
components. Expand a kit only after its implementation metadata, Content policy,
recipe validation, and edit/reload checks agree.

## Titles, properties, and columns

Canvas title fields write the existing declared property. A populated title
slot keeps its rich content instead of being flattened into a text property.
Variant changes preserve properties and children and must pass the full Content
policy. An incompatible switch leaves the document unchanged.

Column presets are exactly Small / Large, Medium / Medium, and Large / Small.
The divider changes both widths as one undoable edit. Imported custom widths
and layouts with another number of columns remain unchanged on opening. The
editor does not infer heading sections or restructure a document automatically.

## Host components and named slots

A host can combine its own source with the layout kit through
`composeAuthoringKits`. This function validates the combined kit. Use
`createAuthoringKit` to validate a single source. The builder
checks implementation metadata against the policy and validates every recipe.
It freezes the provided configuration before asynchronous validation starts;
pass a fresh object if the host needs an editable configuration draft.

Declare named slots in both the implementation metadata and Content policy.
Authoring metadata can give each slot a readable label. The editor preserves
separate default and named content through visual edits and source conversion.
The playground's `learning-objective` component demonstrates `default` and `tip`:

```mdc
<learning-objective title="Understand the contract" assessed>
Explain the outcome.

<template #tip>
Keep the example concrete.
</template>
</learning-objective>
```

This is a host example, not a built-in Docs tag. The layout kit keeps the named
slots of cards and accordion items in the document, but the canvas edits only
their default slots and their text properties.

## Source safety and preview

The canonical value is Markdown/MDC source, not TipTap JSON. The editor opens
visual mode only after parsing, schema conversion, and a semantic round-trip
check succeed. Unsupported or invalid documents stay in Markdown with their
original source available. Opening, closing, or changing modes does not rewrite
source. A real visual edit may normalize formatting while preserving meaning.

Unsupported paste leaves the current document unchanged. A failed conversion
keeps pending visual work and blocks switching to Markdown until the author can
recover. Hosts must respect a failed `flush()` before closing or changing the
document.

The `recipe-preview` slot receives `{ recipe }`. Render `recipe.source` through
Ginko Content with the same policy and registered host components. This shows
the actual reading component; the stable writing canvas is not an exact copy of
interactive tabs, quizzes, or other application UI. A renderer preview cannot
make unsupported visual editing safe.

Native Markdown tables keep their first row as a header and support column
alignment. Merged cells and persisted column widths are outside that contract.
HTML, arbitrary Vue expressions, and arbitrary editor extension injection are
not an escape route around Content validation.
